# Практическая работа: балансировка нагрузки (Load Balancing)

Готовый учебный проект: три статических веб-сервера NGINX и один NGINX-балансировщик в Docker Compose.

## Что находится в архиве

```text
load-balancer-project/
├── docker-compose.yml
├── start.bat
├── stop.bat
├── nginx/
│   └── nginx.conf
├── server1/
│   └── index.html
├── server2/
│   └── index.html
├── server3/
│   └── index.html
├── scripts/
│   └── test-load-balancing.ps1
├── README.md
└── REPORT-TEMPLATE.md
```

## Перед запуском

1. Установите Docker Desktop: https://www.docker.com/products/docker-desktop/
2. Запустите Docker Desktop и дождитесь состояния **Engine running**.
3. Распакуйте архив.
4. Откройте папку `load-balancer-project` в Visual Studio Code.
5. В файле `server3/index.html` замените `ВПИШИТЕ_СВОЮ_ГРУППУ` на название своей группы.

Проверьте Docker в терминале VS Code:

```powershell
docker --version
docker compose version
```

## Запуск

**Самый простой способ:** дважды щёлкните `start.bat`.

Либо в терминале VS Code, находясь в папке проекта, выполните:

```powershell
docker compose up -d
docker compose ps
```

При первом запуске Docker загрузит образ `nginx:alpine`, поэтому потребуется интернет. После запуска должны быть видны четыре контейнера.

Откройте в браузере:

http://localhost:8080

## Проверка распределения запросов

В PowerShell из корневой папки проекта выполните:

```powershell
1..9 | ForEach-Object {
    (Invoke-WebRequest http://localhost:8080 -UseBasicParsing).Content
}
```

Или запустите готовый скрипт:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\test-load-balancing.ps1
```

В ответах должны встречаться `SERVER 1`, `SERVER 2` и `SERVER 3`. NGINX использует Round Robin по умолчанию: распределяет последовательные новые запросы между доступными серверами по очереди. Из-за повторных попыток, ошибок и состояния узлов последовательность при сбоях может отличаться.

## Проверка отказоустойчивости

Остановите первый сервер:

```powershell
docker compose stop server1
docker compose ps
```

Отправьте запросы повторно:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\test-load-balancing.ps1 -Count 6
```

Запросы должны обслуживаться оставшимися серверами. При первом обращении к остановленному узлу возможна задержка: NGINX использует пассивное обнаружение отказов и узнаёт о проблеме по фактической ошибке запроса.

Восстановите сервер:

```powershell
docker compose start server1
docker compose ps
```

Повторите проверку. После восстановления сервер снова сможет участвовать в обработке запросов.

## Дополнительное задание

1. Укажите свою группу в `server3/index.html`.
2. Если контейнеры уже запущены, изменения HTML-файла обычно становятся видны сразу, так как папка подключена как volume. Для повторного запуска всей инфраструктуры используйте:

   ```powershell
   docker compose down
   docker compose up -d
   ```

3. Отключите второй сервер:

   ```powershell
   docker compose stop server2
   ```

4. Проверьте запросы:

   ```powershell
   powershell -ExecutionPolicy Bypass -File .\scripts\test-load-balancing.ps1 -Count 6
   ```

5. Восстановите его:

   ```powershell
   docker compose start server2
   ```

## Остановка и удаление контейнеров

```powershell
docker compose down
```

Или дважды щёлкните `stop.bat`. Команда удаляет контейнеры и сеть проекта, но не удаляет исходные файлы проекта и загруженный образ.

## Для чего нужны основные директивы NGINX

- `upstream backend_servers` — объявляет группу серверов, на которые балансировщик может отправлять запросы.
- `server server1:80` — имя сервиса Docker Compose и порт веб-сервера внутри сети Docker.
- `listen 80` — порт, который слушает NGINX внутри контейнера балансировщика.
- `proxy_pass http://backend_servers` — передаёт запрос выбранному серверу из группы `upstream`.
- `max_fails=1` — число неудачных попыток, после которого сервер считается недоступным в рамках пассивного контроля.
- `fail_timeout=10s` — период, в течение которого учитываются ошибки, и время временного исключения сервера после достижения порога.
- `proxy_next_upstream` — указывает, при каких ошибках можно попробовать другой сервер.
- `proxy_next_upstream_tries 3` — ограничивает число попыток проксирования.

**Важно:** в NGINX Open Source здесь используется пассивное обнаружение отказов, а не постоянная активная проверка серверов. Поэтому первая ошибка при обращении к остановленному серверу возможна; директивы повторной попытки помогают переключить запрос на другой узел.

## Основные параметры Docker Compose

- `services` — список контейнеризуемых сервисов проекта.
- `image` — Docker-образ, из которого создаётся контейнер.
- `volumes` — подключает локальную папку или файл внутрь контейнера.
- `ports` — публикует порт контейнера на компьютере. Здесь `8080:80` означает порт 8080 на компьютере и порт 80 внутри контейнера.
- `depends_on` — задаёт порядок запуска: сначала серверы, затем балансировщик. Сам по себе не гарантирует, что приложение внутри зависимого контейнера уже полностью готово.
- `restart: unless-stopped` — автоматически перезапускает контейнер при сбое, если его не остановили вручную.

## Частые проблемы

- **`docker` не найден:** перезапустите терминал после установки Docker Desktop или проверьте установку.
- **Docker Engine недоступен:** запустите Docker Desktop и дождитесь готовности.
- **Порт 8080 занят:** измените слева в `ports` значение `8080:80`, например на `8081:80`, и открывайте `http://localhost:8081`.
- **Страница не открывается сразу:** подождите несколько секунд и проверьте `docker compose ps` и `docker compose logs loadbalancer`.
- **PowerShell блокирует запуск скрипта:** используйте команду с `-ExecutionPolicy Bypass`, приведённую выше.

Подробный шаблон отчёта и ответы на контрольные вопросы находятся в `REPORT-TEMPLATE.md`.
